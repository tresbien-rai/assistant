1. ACCEPTANCE CRITERIA
================================================================================

AC-1: Avatar upload, retrieval, and deletion work
  PASS
  - POST /:id/avatar handles upload via multer with `upload.single('avatar')`.
  - GET /:personaId/avatar retrieves via `res.sendFile()` with content-type
    auto-detected by Express.
  - DELETE /:id/avatar removes file via safeDelete and clears DB reference.
  - Stale references are self-healing (if file is missing, DB is cleared on
    next GET).

AC-2: Expression image upload, retrieval, and deletion work
  PASS
  - POST /:id/expressions/:name/image uploads, stores in expressions JSON.
  - GET /:personaId/expressions/:name serves the file.
  - DELETE /:id/expressions/:name/image deletes file and clears imageKey.
  - Expression name is validated (alphanumeric, hyphens, underscores, max 50).

AC-3: Non-image files are rejected with VALIDATION_ERROR
  PASS
  - fileFilter checks `file.mimetype` against ALLOWED_MIME_TYPES whitelist.
  - Rejection creates `new AppError(400, 'VALIDATION_ERROR', ...)` -- correct
    code and status.
  - handleMulterError middleware properly converts/forwards the error.

AC-4: Files over 5MB are rejected
  PASS
  - `limits: { fileSize: 5 * 1024 * 1024 }` in multer config.
  - handleMulterError converts LIMIT_FILE_SIZE to AppError.validation().

AC-5: Avatar URLs are accessible and serve correct content-type
  PASS
  - `res.sendFile(filePath)` automatically sets Content-Type based on
    file extension.
  - Cache-Control header is set: `private, max-age=3600, must-revalidate`.

AC-6: Cannot upload to another user's persona (returns 404)
  PASS
  - All upload/delete/serve routes call `dal.getPersonaById(personaId, userId)`
    which filters by `user_id` in the WHERE clause.
  - Returns 404 (AppError.notFound) if persona not found or not owned,
    preventing information disclosure.

2. BUGS AND SECURITY ISSUES
================================================================================

[Major] S-1: Potential path traversal in avatar serving routes via
            persona.avatar_filename

  Location: avatars.js lines 354, 389
  Code:
    const filePath = path.join(AVATARS_DIR, persona.avatar_filename);
    // and:
    const filePath = path.join(AVATARS_DIR, expr.imageKey);

  The serving routes read `avatar_filename` and `imageKey` from the database
  and use them in `path.join(AVATARS_DIR, ...)` then `res.sendFile(filePath)`.
  Since the upload routes are the ones that SET these values, and they use
  controlled filenames (`${personaId}_avatar${ext}`), the database values
  should always be safe under normal operation.

  However, if any other code path or direct DB manipulation were to set
  `avatar_filename` to something like `../../etc/passwd`, `path.join` would
  resolve to a path outside AVATARS_DIR. A defense-in-depth approach would
  add a check like:
    const resolved = path.resolve(AVATARS_DIR, filename);
    if (!resolved.startsWith(AVATARS_DIR)) throw AppError.validation(...)

  Risk: Low in practice (requires DB tampering), but it is a missing layer
  of defense. Standard security practice for file serving.

  Severity: Major (defense-in-depth gap)

----------

[Minor] S-2: personaId is not validated before use in filenames

  Location: avatars.js lines 92, 103 (avatarFilename, expressionFilename)

  The personaId comes from URL params (`:id` / `:personaId`) and is used
  directly in constructing filenames. In this codebase, persona IDs are UUIDs
  generated by the DAL, so they should always be alphanumeric+hyphens. But
  there is no explicit validation that the ID is a valid UUID before it is
  used in the filename. If someone sends a crafted personaId like
  `../../etc/passwd`, the path.join would escape the avatars directory.

  The `dal.getPersonaById` call that follows will return null for any invalid
  ID, causing a 404. For the upload routes, this means the temp file gets
  cleaned up (good). For serving routes, the sendFile never executes.

  But there is a subtle ordering issue on upload: the multer middleware saves
  the temp file BEFORE the route handler runs and validates the personaId.
  The temp file is cleaned up if persona is not found, so no data leak, but
  the personaId is never used in the temp filename (it uses `tmp_${Date.now()}`
  pattern), so this is not exploitable.

  Still, adding UUID validation on personaId would be a clean improvement.

  Severity: Minor (not exploitable due to DAL check + temp filename pattern)

----------

[Minor] S-3: Temp file cleanup race with file filter rejection

  Location: avatars.js lines 67-73, 180, 251

  When the fileFilter rejects a file (wrong MIME type), multer passes the
  error to the handleMulterError middleware. In multer v2 with diskStorage,
  if the file filter rejects, the file should not be written to disk at all
  (the filter runs before writing). This is correct behavior.

  However, if the file IS written (e.g., multer v2 behavior edge cases), and
  then an error occurs in the route handler AFTER renameSync, there is no
  rollback. This is acceptable since the rename is essentially the last
  critical operation before the DB update.

  Severity: Minor (theoretical only)

----------

[Minor] S-4: SVG files accepted -- potential XSS vector

  Location: avatars.js line 40

  `image/svg+xml` is in the ALLOWED_MIME_TYPES list. SVG files can contain
  embedded JavaScript. If these are ever served with `Content-Type: image/svg+xml`
  (which `res.sendFile` will do for .svg files), a browser rendering the
  response directly could execute the embedded script.

  The serving routes require authentication, and the files are served from
  an API path (not directly embedded), so exploitation requires the victim
  to navigate directly to the avatar URL. Additionally, Cache-Control is
  set to `private`.

  This is a known trade-off. If SVG support is intentional, consider serving
  SVGs with `Content-Disposition: attachment` or stripping/sanitizing them.

  Severity: Minor (requires auth, API path reduces exposure)

================================================================================

[PASS] Route structure:

    router (servingRouter), exported as named exports.
  - Mounting in index.js is clear and properly namespaced.

[PASS] Naming conventions:

  - Router exports (personaAvatarRouter, avatarServingRouter) are descriptive.

[PASS] Consistency with existing routes:
  - Uses the same `router.use(authenticate)` pattern as apiKeys, conversations,
    and settings routes.
  - Uses dal.getPersonaById for ownership verification, same as other routes
    would.
  - Uses asyncHandler wrapper consistently.

[PASS] Logging:
  - Upload and delete operations are logged at info level with relevant context.
  - File deletion failures (non-ENOENT) logged at warn level.

[PASS] Self-healing stale references:
  - Both GET endpoints check if the file exists on disk. If the DB says there
    is an avatar/expression image but the file is missing, the DB reference is
    cleared. This is a nice touch for robustness.

[PASS] Gitignore and directory setup:
  - `server/data/avatars/*` is gitignored, `!server/data/avatars/.gitkeep`
    preserves the directory. Correct pattern.

----------

[Nit] Q-1: Synchronous filesystem operations

  The code uses `fs.readdirSync`, `fs.unlinkSync`, `fs.renameSync`, and
  `fs.existsSync`. These are blocking and could cause latency under high
  concurrency. For a single-user or low-traffic application, this is fine.
  For a production system at scale, the async equivalents (fs.promises)
  would be preferable.

  Severity: Nit (acceptable for current scale)

----------

[Nit] Q-2: Temp filename collision potential

  Location: avatars.js line 63

  `tmp_${Date.now()}${ext}` could collide if two uploads happen in the same
  millisecond. Extremely unlikely in practice. Using crypto.randomUUID() or
  similar would eliminate the possibility entirely.

  Severity: Nit

----------

[Nit] Q-3: No explicit AVATARS_DIR creation at startup

  The code assumes `server/data/avatars/` exists. The .gitkeep file ensures
  it exists in the repo, but if someone deletes it or deploys without it,
  multer will throw ENOENT. Consider adding an `fs.mkdirSync(AVATARS_DIR,
  { recursive: true })` at module load time, similar to how some projects
  ensure directories exist.

  Severity: Nit (gitkeep handles normal case)

Overall: PASS -- Ready to merge with minor recommendations.

The implementation correctly meets all 6 acceptance criteria. The code is
well-structured, follows existing patterns, and handles edge cases
thoughtfully (stale reference cleanup, temp file cleanup on persona-not-found).

Recommended actions before merge (none are blockers):

     filenames are currently always controlled, a simple

     important defense-in-depth. (~2 lines of code per serving route)

  2. [Minor] Consider validating personaId as a UUID format in the routes

     'image/svg+xml' from ALLOWED_MIME_TYPES to eliminate the XSS vector
     entirely.
